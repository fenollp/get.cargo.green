Your team rebuilds the same dependencies all day.

Your laptop's target/ only helps you. Your teammates and CI rebuild the same serde, tokio and hundreds of other crates on every machine, branch and pull request. That costs minutes per build and a CI bill for compiling code nobody changed.

Local caches stay local

target/ belongs to one machine. A fresh clone, a new worktree or a new CI runner starts from zero.

Shared caches miss

Tools that copy compiled files between machines miss when paths, toolchains or system libraries differ.

CI caches are all-or-nothing

Most CI caches store one archive keyed on Cargo.lock. Bump one dependency and the whole cache misses.

Cache each crate, the same way on every machine.

cargo green builds each crate in an isolated, pinned environment using BuildKit or Nix. The same crate gets the same cache key on every machine, so a teammate's build or a CI job can reuse yours. Results are stored in a registry you control.

Build once. Reuse everywhere.

  • Change one crate, rebuild one crate (and what depends on it)
  • Cache hits across laptops, CI runners and build servers
  • Covers proc-macros, build scripts and linking
  • Compile on a remote machine over SSH
  • Still cargo: no new build system to learn

Faster from the first CI job.

No warm-up and no lockfile matching. The first job against a shared cache skips every crate someone already built.

Not keyed on Cargo.lock

Bump one dependency and only that crate and its dependents rebuild.

Downloads during the build

Cached crates download while compilation runs. No restore step blocking the job.

No cache steps

Remove the cache save/restore actions from your workflow. Nothing to archive, upload or expire.

One install. One extra word.

cargo green is a cargo plugin. Your commands, Cargo.toml and CI stay the same.

Full installation docs 
# From crates.io
cargo install cargo-green

# …or track the latest from git
cargo install --locked --force \
  --git https://github.com/fenollp/supergreen.git cargo-green

# Make sure $CARGO_HOME/bin is on your $PATH
which cargo-green

# Needs one build engine on the machine to write to cache:
#   a docker or podman client, or nix.
# Once: start from a clean slate
cargo clean

# Then use cargo, with one extra word
cargo green build
cargo green test
cargo green clippy

# Like it? Make it invisible
alias cargo='cargo green'

# Pick your engine: docker (default), podman, or nix
export CARGOGREEN_RUNNER=nix

# Plain `cargo build` keeps working afterwards.
# Compile on the 96-core box, run the binary locally
DOCKER_HOST=ssh://build-farm-01 cargo green test

# Same idea with the Nix engine
CARGOGREEN_RUNNER=nix NIX_SSHOPTS="-A" \
  cargo green build --release

# Laptops stay quiet. Fans stay off.
# Cargo.toml
[package.metadata.green]
cache-images = [
  "docker-image://ghcr.io/acme/payments-api",
]
cache-from-images = [
  "docker-image://ghcr.io/acme/global-cache",
]

# Push the cache for everyone else
cargo green supergreen push
# .github/workflows/ci.yml
- run: cargo install cargo-green
- run: cargo green test
  env:
    CARGOGREEN_CACHE_IMAGES: docker-image://ghcr.io/acme/api

# Warm the cache for offline / air-gapped runners
- run: cargo green supergreen sync

Wrap, translate, build, share.

cargo green plugs into $RUSTC_WRAPPER, a hook cargo already supports. Four steps run between cargo green build and your binary.

  1. 01

    Wrap

    cargo green sets $RUSTC_WRAPPER and runs cargo. cargo still resolves and schedules your build.

  2. 02

    Translate

    Each rustc call and build script becomes an isolated build step, pinned to your exact toolchain.

  3. 03

    Build

    Nix or BuildKit (Docker, Podman) runs the steps in parallel, locally or on a remote machine.

  4. 04

    Cache & share

    Each crate's result is fetched from or sent to storage. You, your team, CI and the World share one cache.

Why the cache hits on other machines

Two machines building the same crate usually produce different keys. cargo green removes the differences:

  • The build environment is pinned, not taken from the host
  • Paths are normalized, so your $HOME never enters a cache key
  • Git dependencies are pinned to an exact revision
  • Outputs are reproducible, down to file timestamps

Bonus: builds are auditable. You can show what produced a binary and rebuild it later to prove it.

Two engines, one workflow

Use the engine your team already has. Commands, config and cached results work the same with both.

BuildKit

Uses your docker or podman client. Cache lives in any OCI registry.

runner = "docker" | "podman"

Nix

For teams on nix. Cache lives in a Nix binary cache, still per crate.

runner = "nix"

Laptops don't need to run a daemon. Point cargo green at a shared machine and it does the compiling.

Works by default. Configurable when needed.

Set options in [package.metadata.green] in Cargo.toml, or with $CARGOGREEN_* environment variables. Environment variables take precedence, which suits CI.

Common questions

Do I have to change my workflow?

No. Run cargo clean once, then use cargo green build like cargo build. It produces the same files. Plain cargo build still works, so you can stop any time.

Does this lock us in?

No. The CLI is open source (AGPL-3.0) and the cache is plain content in a registry you choose. Switch registries with one line of config.

Do we need Docker on every developer machine?

No. To read from the public cache, you need no engine at all. To build, you need a docker or podman client, or Nix, and the compiling can happen on a shared remote machine instead of the laptop.

How is this different from sccache or cargo-chef?

sccache needs matching paths and environments across machines, can't cache linking, struggles with proc-macros, and with a remote backend checking the cache can take longer than compiling. cargo-chef caches all dependencies as one Docker layer, so one bump rebuilds them all. cargo-green builds each crate in a pinned, isolated step: keys match across machines, caching is per crate, and a partial match still saves work. See the full comparison in the README.

BuildKit or Nix?

The one you already use. Most teams have docker or podman, so that's the default. On Nix, use Nix and keep your binary cache. Commands, config and results are the same, and both can share hits.

How soon does CI get faster?

On the first job. Cached crates download during the build instead of in a restore step first. A branch that bumps a dependency still reuses everything else.

Can it build without network access?

Yes. cargo green supergreen sync downloads every image and crate up front; builds then need no network. Air-gapped setups are supported on Enterprise.

What is free?

Reading the planet-wide public cache: no account needed. Writing to it: free once signed in. Using your own registry: always free. Paid plans cover a private cache, hosted by us or on-premise.

What counts as a cache request?

One read or write of one cached crate. A warm build of a 400-crate workspace is about 400 requests, so 10 million covers a busy team's laptops and CI. Usage shows in the dashboard before it shows on an invoice.

Where is the source code?

On GitHub, under AGPL-3.0. Issues and pull requests are welcome.
